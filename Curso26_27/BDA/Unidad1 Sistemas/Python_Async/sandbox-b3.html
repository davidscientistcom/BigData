Primitivas de Sincronización y Exclusión Mutua

Prevención de condiciones de carrera sobre memoria compartida con Locks y limitación de tasa y descriptores de red con Semáforos.

E3.0: Corrupción de Estado por Condición de Carrera (Race Condition)

Objetivo Técnico: Desmitificar el concepto erróneo de que la programación asíncrona monohilo es inmune a las condiciones de carrera. Cuando dos o más corrutinas realizan una secuencia de lectura-modificación-escritura sobre una variable mutable y ocurre un cambio de contexto (await) en medio de la operación, los datos se corrompen.

python — e3_0_race_condition.py 
import asyncio

balance_cuenta = 0

async def acreditar_fondos():
    global balance_cuenta
    # 1. Lectura del estado actual
    lectura_temporal = balance_cuenta
    # 2. Simulación de operación I/O intermedia que cede el hilo de ejecución
    await asyncio.sleep(0.001)
    # 3. Escritura no atómica sobre una referencia desactualizada
    balance_cuenta = lectura_temporal + 10

async def main():
    iteraciones = 100
    # 100 operaciones de +10 deberían totalizar 1000
    tareas = [acreditar_fondos() for _ in range(iteraciones)]
    await asyncio.gather(*tareas)
    
    print(f"[REPORTE] Balance esperado: {iteraciones * 10}")
    print(f"[REPORTE] Balance real obtenido: {balance_cuenta}")

if __name__ == "__main__":
    asyncio.run(main())
Análisis de Pérdida de Datos: El valor esperado es 1000, pero el valor final obtenido ronda 10. Las 100 corrutinas leyeron el estado inicial 0 antes de que la primera pudiera escribir, sobrescribiéndose masivamente entre sí. El entrelazamiento de tareas produce inconsistencias idénticas a las del modelo multihilo.

E3.1: Exclusión Mutua en la Sección Crítica (asyncio.Lock)

Objetivo Técnico: Garantizar la atomicidad en la sección crítica mediante asyncio.Lock(). Utilizando el protocolo de gestión de contexto asíncrono (async with lock), solo una corrutina puede acceder a la modificación del recurso simultáneamente.

python — e3_1_mutex_lock.py 
import asyncio

balance_cuenta = 0
mutex_balance = asyncio.Lock()

async def acreditar_fondos_seguro():
    global balance_cuenta
    # Serialización determinista de la sección crítica
    async with mutex_balance:
        lectura_temporal = balance_cuenta
        await asyncio.sleep(0.001)  # I/O seguro: ninguna otra tarea puede entrar aquí
        balance_cuenta = lectura_temporal + 10

async def main():
    iteraciones = 100
    tareas = [acreditar_fondos_seguro() for _ in range(iteraciones)]
    await asyncio.gather(*tareas)
    
    print(f"[REPORTE] Balance esperado: {iteraciones * 10}")
    print(f"[REPORTE] Balance protegido con Lock: {balance_cuenta}")

if __name__ == "__main__":
    asyncio.run(main())
Resultado: El balance resultante es exactamente 1000. Las corrutinas que intentan adquirir el lock mientras está ocupado son puestas en cola de espera sin bloquear el hilo del sistema operativo.

E3.2: Control de Concurrencia y Saturación (asyncio.Semaphore)

Objetivo Técnico: Limitar el grado de paralelismo en operaciones intensivas de red mediante asyncio.Semaphore(N). Permite un máximo de N operaciones concurrentes para prevenir el agotamiento de file descriptors (Errno 24: Too many open files) o bloqueos por rate limiting HTTP 429.

python — e3_2_semaphore_rate_limit.py 
import asyncio

# Límite estricto de 3 operaciones concurrentes
pool_conexiones = asyncio.Semaphore(3)

async def consultar_nodo(id_nodo: int):
    async with pool_conexiones:
        print(f"[SLOT-ACQUIRED] Nodo {id_nodo} accediendo al pool activo...")
        await asyncio.sleep(1.0)  # Simulación de latencia de red
        print(f"[SLOT-RELEASED] Nodo {id_nodo} liberando slot.")

async def main():
    total_consultas = 10
    print(f"[POOL] Encolando {total_consultas} tareas con semáforo limitado a 3 slots...")
    tareas = [consultar_nodo(i) for i in range(1, total_consultas + 1)]
    await asyncio.gather(*tareas)
    print("[POOL] Todas las consultas han sido procesadas de forma controlada.")

if __name__ == "__main__":
    asyncio.run(main())
Regla de Dimensionamiento: A diferencia de un Lock (semáforo binario de capacidad 1), un Semaphore permite calibrar el caudal de salida según la capacidad del backend (ej. número de conexiones simultáneas del pool de PostgreSQL o el límite de concurrencia de un API Gateway).
