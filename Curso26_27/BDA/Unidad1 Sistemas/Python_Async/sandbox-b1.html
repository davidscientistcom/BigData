Event Loop y E/S No Bloqueante

Comprender la diferencia fundamental entre el bloqueo del hilo del sistema operativo y la suspensión cooperativa de corrutinas en CPython.

E1.0: Bloqueo Síncrono del Hilo Principal (time.sleep)

Objetivo Técnico: Comprobar el efecto de invocar llamadas bloqueantes dentro de un contexto asíncrono. Cuando una rutina ejecuta una función síncrona que bloquea el hilo del sistema operativo (como time.sleep o una llamada de socket sin soporte async), todo el Event Loop se congela, impidiendo que cualquier otra corrutina progrese.

python — e1_0_bloqueo_sincrono.py 
import asyncio
import time

async def tarea_bloqueante(id_tarea: int):
    print(f"[INFO] [Tarea {id_tarea}] Iniciando fase de espera...")
    # ERROR CRÍTICO: Bloqueo de hilo a nivel de SO (detiene todo el proceso)
    time.sleep(2)
    print(f"[INFO] [Tarea {id_tarea}] Espera finalizada.")

async def main():
    print("[INIT] Inicializando Event Loop...")
    # Intentamos concurrir ambas tareas
    await asyncio.gather(
        tarea_bloqueante(1),
        tarea_bloqueante(2)
    )
    print("[DONE] Ejecución completada.")

if __name__ == "__main__":
    t_inicio = time.time()
    asyncio.run(main())
    print(f"[BENCHMARK] Tiempo total: {time.time() - t_inicio:.2f} segundos")
Diagnóstico: El tiempo total de ejecución es de 4.0 segundos (2s + 2s). A pesar de emplear asyncio.gather(), time.sleep() no devuelve el control al planificador de eventos; por consiguiente, la Tarea 2 no puede inicializarse hasta que la Tarea 1 desaloja completamente el procesador.

E1.1: Concurrencia Cooperativa y Suspensión (asyncio.sleep)

Objetivo Técnico: Sustituir la detención del hilo por una suspensión cooperativa mediante await asyncio.sleep(). Al pausar la corrutina en una llamada asíncrona no bloqueante, el control de la CPU se devuelve al Event Loop, permitiendo que otras corrutinas pendientes consuman ciclos de reloj.

python — e1_1_concurrencia_cooperativa.py 
import asyncio
import time

async def tarea_cooperativa(id_tarea: int):
    print(f"[INFO] [Tarea {id_tarea}] Iniciando espera asíncrona...")
    # CORRECTO: Cede voluntariamente el control al planificador del Event Loop
    await asyncio.sleep(2)
    print(f"[INFO] [Tarea {id_tarea}] Reanudación tras espera.")

async def main():
    print("[INIT] Inicializando Event Loop...")
    await asyncio.gather(
        tarea_cooperativa(1),
        tarea_cooperativa(2)
    )
    print("[DONE] Ambas tareas finalizadas concurrentemente.")

if __name__ == "__main__":
    t_inicio = time.time()
    asyncio.run(main())
    print(f"[BENCHMARK] Tiempo total: {time.time() - t_inicio:.2f} segundos")
Diagnóstico: El tiempo total es de solo 2.0 segundos. La Tarea 1 ejecuta hasta alcanzar el punto de suspensión await, momento en el que el bucle transfiere inmediatamente la ejecución a la Tarea 2. Ambas esperas de E/S se solapan en paralelo sobre el mismo hilo.

E1.2: Resolución Asíncrona Múltiple (asyncio.gather)

Objetivo Técnico: Observar cómo asyncio.gather() preserva de forma determinista el orden del vector de resultados retornado, con independencia de que las operaciones subyacentes terminen en momentos y secuencias distintas debido a variaciones en la latencia de red.

python — e1_2_agregacion_gather.py 
import asyncio

async def descargar_recurso(nombre: str, latencia_s: float) -> str:
    print(f"[I/O] [{nombre}] Iniciando petición (latencia estimada: {latencia_s}s)...")
    await asyncio.sleep(latencia_s)
    print(f"[I/O] [{nombre}] Respuesta recibida tras {latencia_s}s.")
    return f"PAYLOAD_{nombre.upper()}"

async def main():
    print("[INIT] Lanzando peticiones asíncronas simultáneas...")
    # Orden de paso: Video (3s), Imagen (1s), Metadatos (0.5s)
    resultados = await asyncio.gather(
        descargar_recurso("Video", 3.0),
        descargar_recurso("Imagen", 1.0),
        descargar_recurso("Metadatos", 0.5)
    )
    print(f"[DONE] Vector de resultados en orden de invocación original:
       {resultados}")

if __name__ == "__main__":
    asyncio.run(main())
Observación Arquitectural: El recurso "Metadatos" finaliza en 0.5s y "Imagen" en 1.0s, mucho antes que "Video". Sin embargo, gather() devuelve ['PAYLOAD_VIDEO', 'PAYLOAD_IMAGEN', 'PAYLOAD_METADATOS'] manteniendo intacta la correspondencia posicional con la firma de llamada.
