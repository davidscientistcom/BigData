Configuración Completa de SSH por Clave Pública

Elimina las contraseñas para siempre: criptografía asimétrica, protección contra ataques Man-in-the-Middle con Fingerprints y despliegue de authorized_keys con permisos estrictos.

1. El Fin de las Contraseñas: Criptografía Asimétrica en SSH

En administración de servidores de Big Data (clusters de Spark, nodos Kafka, Kubernetes), nadie entra a los servidores tecleando una contraseña interactiva. Las contraseñas son vulnerables a ataques de fuerza bruta, no son automatizables en pipelines y suponen un riesgo crítico de seguridad.

El estándar de la industria es la autenticación asimétrica por par de claves (Key-based Authentication):

Esquema Criptográfico: Desafío y Respuesta SSH
✦ Clave Privada (Private Key)

Es tu firma digital exclusiva. Se almacena en tu equipo local bajo permisos restrictivos. Bajo ningún concepto debe enviarse por correo, subirse a GitHub ni compartirse.

✦ Clave Pública (Public Key)

Es la "cerradura" que abres con tu llave privada. Se añade en el archivo ~/.ssh/authorized_keys del servidor. Cualquiera puede ver tu clave pública sin comprometer tu seguridad.

2. Paso 1: Instalación y Verificación del Servidor OpenSSH

Inicia sesión en la consola de Ubuntu Server en VirtualBox y asegúrate de que el servicio de SSH está instalado y en ejecución:

bash 
# 1. Actualiza repositorios e instala OpenSSH Server
sudo apt update && sudo apt install -y openssh-server

# 2. Habilita e inicia el servicio para que arranque automáticamente al encender la VM
sudo systemctl enable --now ssh

# 3. Comprueba el estado del demonio SSH
sudo systemctl status ssh

El servicio debe mostrar Active: active (running) con un punto verde, escuchando en el puerto estándar 22.

3. Paso 2: El Misterio del Fingerprint y 'known_hosts'

Cuando te conectas por primera vez por SSH desde tu terminal anfitrión (Windows PowerShell o Terminal en macOS/Linux):

terminal anfitrión 
ssh alumno@192.168.56.10

Aparece el siguiente mensaje que desconcierta a los principiantes:

alerta de seguridad ssh 
The authenticity of host '192.168.56.10 (192.168.56.10)' can't be established.
ED25519 key fingerprint is SHA256:abc123def456ghi789...
Are you sure you want to continue connecting (yes/no/[fingerprint])?
ℹ️
¿Qué es el Fingerprint y para qué sirve?
El fingerprint es el hash criptográfico (huella digital) de la clave pública del servidor. Sirve para protegerte contra ataques Man-in-the-Middle (MitM). Al escribir yes, tu cliente SSH guarda esa huella en el archivo local ~/.ssh/known_hosts. Si en el futuro alguien suplanta la IP de tu servidor, SSH detectará que la huella no coincide, abortará la conexión y te lanzará una alarma de seguridad.

4. Paso 3: Generar tu Par de Claves en tu Ordenador Anfitrión

En tu ordenador personal (desde donde te conectas, NO dentro de la máquina virtual), abre una terminal y genera un par de claves moderno:

Opción A (Recomendada): ED25519

bash / powershell 
ssh-keygen -t ed25519 -C "tu_nombre@bda"

Curva elíptica de última generación: claves más cortas, cálculo ultrarrápido y máxima resistencia a ataques.

Opción B: RSA de 4096 bits

bash / powershell 
ssh-keygen -t rsa -b 4096 -C "tu_nombre@bda"

Estándar clásico compatible con sistemas legados.

El comando te preguntará dónde guardar el archivo (presiona ENTER para aceptar la ruta predeterminada ~/.ssh/id_ed25519) y si deseas una contraseña de cifrado (passphrase). Para este laboratorio de desarrollo, puedes presionar ENTER dos veces para dejarla sin contraseña.

5. Paso 4: Copiar la Clave Pública al Servidor

Para que el servidor reconozca tu clave pública, debe insertarse en ~/.ssh/authorized_keys del usuario en la VM.

Método Rápido: Usando 'ssh-copy-id'

En macOS, Linux y Windows 10/11 con OpenSSH habilitado:

terminal anfitrión 
ssh-copy-id -i ~/.ssh/id_ed25519.pub alumno@192.168.56.10

Te pedirá la contraseña del usuario en la VM por última vez. ssh-copy-id se encarga automáticamente de crear el directorio ~/.ssh, asignar los permisos exactos y añadir la clave sin sobreescribir las que ya existan.

Método Manual: Inyección por tubería SSH

Si por algún motivo tu terminal no dispone de ssh-copy-id, puedes inyectar la clave en una sola línea de comando:

powershell / bash 
cat ~/.ssh/id_ed25519.pub | ssh alumno@192.168.56.10 "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"

6. Paso 5: La Regla de los Permisos Estrictos de OpenSSH

🛑
¿Por qué SSH te sigue pidiendo contraseña a pesar de haber copiado la clave?
OpenSSH tiene una directiva de seguridad interna llamada StrictModes. Si el directorio ~/.ssh o el archivo authorized_keys tienen permisos abiertos (por ejemplo, si otros usuarios del sistema pueden leerlos o escribir en ellos), **OpenSSH descarta la clave en silencio por seguridad** y retrocede a pedir contraseña.

En el servidor Ubuntu, ejecuta siempre estos permisos canónicos:

bash (en la máquina virtual) 
# El directorio .ssh solo puede ser accesible por el dueño (700 = rwx------)
chmod 700 ~/.ssh

# El archivo authorized_keys solo puede ser leído/escrito por el dueño (600 = rw-------)
chmod 600 ~/.ssh/authorized_keys

# Verifica que el propietario sea tu usuario (no root)
chown -R $USER:$USER ~/.ssh

7. Paso 6: Blindaje del Servidor (Desactivar Contraseñas)

Una vez que hayas comprobado que puedes conectarte sin contraseña, el paso profesional en entornos productivos es deshabilitar totalmente el login por contraseña para que ningún atacante pueda intentar fuerza bruta:

bash (en la máquina virtual) 
# Edita la configuración del demonio SSH
sudo nano /etc/ssh/sshd_config.d/99-hardened.conf

Añade las siguientes tres directivas de seguridad:

sshd_config 
PasswordAuthentication no
PermitEmptyPasswords no
PubkeyAuthentication yes

Reinicia el servicio para aplicar el blindaje:

bash 
sudo systemctl restart ssh

✓ Lista de Comprobación del Administrador SSH

  • Servidor openssh-server activo y escuchando en el puerto 22.
  • Par de claves id_ed25519 generado en el ordenador local anfitrión.
  • Clave pública inyectada en ~/.ssh/authorized_keys en el servidor.
  • Permisos restrictivos aplicados: chmod 700 ~/.ssh y chmod 600 authorized_keys.
  • Acceso SSH probado con éxito desde el host sin que solicite contraseña.
