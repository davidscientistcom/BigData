Troubleshooting, Redes Residuales y el Misterio de las Claves SSH

Aprende a diagnosticar y resolver los fallos más frustrantes de la virtualización: bloqueos de autenticación SSH por sobreescritura de authorized_keys, adaptadores de red huérfanos en Windows y desincronizaciones de Guest Additions.

1. El Gran Misterio de las Claves SSH en Vagrant

Uno de los problemas más comunes en laboratorios de formación ocurre cuando un alumno intenta configurar claves SSH para Ansible o acceso remoto: de repente, ssh vagrant@192.168.56.x funciona, pero vagrant ssh o vagrant provision empiezan a devolver el temido Permission denied (publickey) o piden contraseña indefinidamente.

El Mecanismo de Inserción de Claves y la Condición de Carrera

¿Qué hace Vagrant por debajo del capó?

  1. Todas las boxes oficiales de Vagrant vienen de fábrica con un par de claves público-privadas idénticas para todo el mundo (insecure_private_key).
  2. En el primer vagrant up, Vagrant entra a la VM usando esa clave insegura pública.
  3. Inmediatamente, por seguridad (config.ssh.insert_key = true por defecto), genera al vuelo un par de claves aleatorias únicas, copia la pública dentro de authorized_keys y guarda la privada en tu carpeta local .vagrant/machines/<nombre>/virtualbox/private_key.
  4. Si en tu script de aprovisionamiento ejecutas cat mi_clave.pub > ~/.ssh/authorized_keys con el operador de sobreescritura (>), eliminas la clave generada por Vagrant. A partir de ese segundo, tú puedes conectar con tu clave personal, pero el comando vagrant ssh y vagrant provision quedan bloqueados sin acceso.

2. Las Dos Soluciones Definitivas al Problema SSH

✦ Solución 1: Coexistencia con '>>' (Recomendada)

En lugar de sobreescribir el archivo, añade tu clave al final utilizando el operador de append (>>). Ambas claves convivirán pacíficamente en authorized_keys:

# ✅ CORRECTO: Ambas claves coexisten
cat /tmp/mi_clave.pub >> /home/vagrant/.ssh/authorized_keys
chmod 600 /home/vagrant/.ssh/authorized_keys
chown -R vagrant:vagrant /home/vagrant/.ssh
✦ Solución 2: Control Declarativo en Vagrantfile

Si quieres usar exclusivamente tu clave personal y desactivar la generación dinámica de claves de Vagrant, indícalo explícitamente:

Vagrant.configure("2") do |config|
  config.vm.box = "ubuntu/jammy64"

  # 1. Desactivar reemplazo automático
  config.ssh.insert_key = false

  # 2. Ruta a tus claves privadas
  config.ssh.private_key_path = [
    "~/.ssh/id_rsa",
    "~/.vagrant.d/insecure_private_key"
  ]
end

3. Adaptadores de Red Residuales en Windows (VERR_INTNET_FLT_IF_NOT_FOUND)

En sistemas operativos Windows, al crear y destruir varias máquinas con red privada (Host-Only), VirtualBox suele dejar adaptadores de red huérfanos o desincronizados en el registro del sistema. Al hacer vagrant up, la consola escupe un error como este:

text — Mensaje de error de VirtualBox 
There was an error while executing `VBoxManage`, a CLI used by Vagrant...
Stderr: VBoxManage.exe: error: Failed to open/create the internal network 
'HostInterfaceNetworking-VirtualBox Host-Only Ethernet Adapter #2' (VERR_INTNET_FLT_IF_NOT_FOUND).
VBoxManage.exe: error: Failed to attach the network LUN (VERR_INTNET_FLT_IF_NOT_FOUND)

Protocolo de Reparación Paso a Paso

1

Listar adaptadores Host-Only en PowerShell

Abre PowerShell en tu sistema anfitrión y consulta los adaptadores registrados:

VBoxManage list hostonlyifs

Observarás nombres duplicados o numerados como VirtualBox Host-Only Ethernet Adapter #2.

2

Eliminar el adaptador corrupto por línea de comandos

Ejecuta el borrado del adaptador residual indicando su nombre exacto:

VBoxManage hostonlyif remove "VirtualBox Host-Only Ethernet Adapter #2"
3

Solución de Purga Definitiva (Si el comando falla)

Si VBoxManage devuelve E_INVALIDARG o no encuentra la interfaz pero el error persiste, cierra VirtualBox completamente y elimina la caché de configuración en tu perfil de usuario de Windows:

# Cerrar procesos huérfanos de VirtualBox en Windows
Stop-Process -Name "VBoxSVC" -Force -ErrorAction SilentlyContinue

# Comprobar la carpeta de configuración global de VirtualBox
# Ruta: C:\Users\\.VirtualBox\VirtualBox.xml

4. Desincronización de Guest Additions y Carpetas Compartidas

Si al hacer vagrant up observas el mensaje de advertencia:

No guest additions were detected on the base box for this VM...
Mounting failed with the error: No such device (mount: unknown filesystem type 'vboxsf')

Significa que el núcleo de Linux de la máquina virtual no tiene cargados los módulos de kernel de VirtualBox necesarios para enlazar las carpetas sincronizadas. La solución oficial recomendada por HashiCorp es instalar el plugin vagrant-vbguest, que detecta y actualiza los controladores automáticamente al arrancar:

bash — Instalación de vagrant-vbguest 
# Instalar plugin en el Host (solo una vez)
vagrant plugin install vagrant-vbguest

# O alternativamente dentro de la VM vía script de aprovisionamiento:
sudo apt-get update -y && sudo apt-get install -y virtualbox-guest-utils

5. Matriz Rápida de Diagnóstico de Incidentes

Síntoma / Error Causa Raíz Acción Correctiva Inmediata
Permission denied (publickey) en vagrant ssh Se sobreescribió authorized_keys con > borrando la clave privada de Vagrant. Cambiar el script a >> o regenerar la VM con vagrant destroy -f && vagrant up.
VERR_INTNET_FLT_IF_NOT_FOUND Adaptador de red Host-Only residual en Windows o subred no permitida (VirtualBox 7). Usar subred 192.168.56.x y ejecutar VBoxManage hostonlyif remove "...".
VT-x is not available / VERR_VMX_NO_VMX La virtualización por hardware está deshabilitada en la BIOS/UEFI del ordenador físico. Reiniciar el PC, entrar a la BIOS/UEFI y habilitar Intel Virtualization Technology (VT-x) o AMD-V / SVM Mode.
Se queda colgado en Waiting for machine to boot... Grub esperando intervención, kernel panic o conflicto de red. Activar vb.gui = true en el Vagrantfile para abrir la ventana visual y observar el log del monitor.
Port collision detected El puerto del host (ej. 8080 o 5432) ya está ocupado por otro servicio. Añadir auto_correct: true a la directiva forwarded_port en el Vagrantfile.

✓ Checklist de Troubleshooting

  • Comprendido el mecanismo de claves SSH inseguras iniciales y la generación de claves en .vagrant/.
  • Verificado que los scripts de provisión utilizan >> para añadir claves a authorized_keys sin sobreescribir.
  • Dominado el uso de VBoxManage list hostonlyifs para sanear adaptadores residuales en Windows.
  • Conocido el truco de vb.gui = true para depurar máquinas congeladas en el arranque.
