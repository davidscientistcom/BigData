2. Los conceptos que hay que tener claros antes de tocar código

2.1 — Qué es HTTP, en cristiano

Ya usas HTTP aunque no lo sepas: cada vez que abres una URL en el navegador, el navegador manda una petición HTTP a un servidor, y el servidor responde con una respuesta. Una petición tiene un método (qué quieres hacer: GET = leer, POST = crear algo nuevo, PUT/DELETE = actualizar/borrar), una ruta (/users/3 = "el usuario número 3"), y opcionalmente un cuerpo (los datos que mandas, normalmente en formato JSON). La respuesta lleva un código de estado (200 = todo bien, 404 = no existe, 500 = el servidor petó) y normalmente también un cuerpo con los datos pedidos.

Eso es literalmente todo lo que necesitas para seguir: microservicios que hablan por HTTP simplemente se mandan peticiones entre ellos, igual que un navegador se las manda a un servidor — la diferencia es que aquí el "cliente" también es un programa, no una persona con un navegador.

2.2 — Servicio

Un servicio (o microservicio) es un programa independiente, con un único trabajo claro, que expone ese trabajo mediante una API — normalmente HTTP. Se puede desplegar, reiniciar y escalar por separado del resto.

2.3 — Contrato / API

El contrato es lo que un servicio promete hacia fuera: qué rutas expone, qué espera recibir, qué va a devolver. Mientras el contrato no cambie, lo que hay dentro del servicio se puede reescribir entero (cambiar de base de datos, de lenguaje, de algoritmo) sin que ningún otro servicio se entere ni se rompa. Esa es la razón de fondo por la que esto soluciona el problema de "equipos grandes se pisan" del módulo anterior: cada equipo solo necesita conocer el contrato de los servicios ajenos, nunca su código interno.

2.4 — Comunicación síncrona vs asíncrona

SíncronaAsíncrona
Un servicio llama a otro por HTTP y espera la respuesta antes de continuar. Simple de razonar (se parece a llamar a una función normal), pero si el otro servicio está caído o lento, tú también te ves afectado. Un servicio publica un mensaje en una cola (ej. RabbitMQ, Kafka) y sigue sin esperar respuesta — otro servicio la recogerá cuando pueda. Más resiliente ante caídas temporales, pero más difícil de razonar (¿y si el mensaje se procesa dos veces? ¿y si nunca se procesa?).

Hoy nos quedamos en síncrona — es donde hay que empezar a entender el patrón antes de complicarlo con colas de mensajes.

2.5 — API Gateway

Un API Gateway es un servicio especial: el único punto de entrada de cara al exterior. El cliente final (una app móvil, un navegador) solo conoce la dirección del gateway — nunca habla directamente con los servicios internos. El gateway recibe la petición y decide a qué servicio interno reenviarla.

¿Por qué no dejar que el cliente hable directo con cada servicio? Porque entonces el cliente tendría que saber cuántos servicios hay y dónde está cada uno — y eso cambiaría cada vez que añades o mueves un servicio. Con el gateway, el cliente ve una sola dirección estable, y todo lo que cambie por dentro es invisible desde fuera.
