6. Probarlo, romperlo, y qué falta para producción

Probarlo de verdad

# Ver usuarios (a través del gateway, puerto 8000 -- el único que "existe" para fuera)
curl http://localhost:8000/users

# Crear un pedido para un usuario que SÍ existe
curl -X POST http://localhost:8000/orders \
  -H "Content-Type: application/json" \
  -d '{"user_id": 3, "item": "libro de causalidad"}'
# -> 201, y por dentro orders-service llamó de verdad a users-service

# Crear un pedido para un usuario que NO existe
curl -X POST http://localhost:8000/orders \
  -H "Content-Type: application/json" \
  -d '{"user_id": 99, "item": "algo"}'
# -> 400 "Ese usuario no existe" -- orders-service lo detectó preguntando a users-service

El experimento que más enseña: romperlo a propósito

Haz esto en clase, en vivo:
  1. Con el sistema levantado, mira qué contenedores hay corriendo: docker compose ps
  2. Para el contenedor de users-service a mano: docker compose stop users-service
  3. Repite la creación de un pedido — va a fallar (un error 500, o un timeout tras 3 segundos, según el momento exacto).
Ese fallo es exactamente lo que en un sistema real hay que diseñar para tolerar. Un monolito no tiene esta clase de fallo — una función que llama a otra función no "se cae" a mitad de la llamada. Un microservicio que llama a otro, sí. Esto se llama fallo parcial, y es el problema central que distingue a los microservicios de un monolito.

Qué falta para un sistema real — con honestidad

Este demo es deliberadamente simple. Un sistema real añadiría, en este orden de importancia:

  • Bases de datos de verdad. Cada servicio con su propia BD (Postgres, por ejemplo) — nunca en memoria, nunca compartida entre servicios.
  • Reintentos y circuit breaker. Si users-service tarda, hoy orders-service se queda esperando sin más. Librerías como tenacity (Python) añaden reintentos automáticos con espera creciente; un circuit breaker corta las llamadas cuando un servicio lleva un rato fallando, para no seguir esperando en vano una y otra vez.
  • Health checks reales en docker-compose.yml, para que depends_on espere de verdad a que un servicio esté listo, no solo arrancado.
  • Service discovery dinámico de verdad (Consul/Kubernetes) — solo hace falta cuando hay docenas de servicios con instancias que suben y bajan solas (auto-escalado). No antes.
  • Observabilidad. Cuando un pedido falla en un sistema con muchos servicios, hace falta ver el rastro completo (gateway → orders → users) en un solo sitio — eso es tracing distribuido (ej. OpenTelemetry).
Preguntas para comprobar que ha quedado claro (antes de cerrar la sesión):
  • ¿Por qué orders-service llama a users-service en vez de tener su propia copia de la lista de usuarios?
  • ¿Qué pasaría si quitáramos el timeout=3.0 de la llamada a users-service?
  • ¿Por qué el cliente nunca llama directamente a users-service o orders-service, solo al gateway?

La regla de oro de todo el curso: cada pieza de la lista de arriba se añade cuando el dolor que resuelve ya existe de verdad — igual que la propia decisión de partir un monolito en microservicios, del módulo 1.
