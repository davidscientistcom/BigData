7. Consul, desde cero y en marcha

Este módulo es autocontenido: no hace falta tocar los tres servicios de antes para empezar. Primero vemos Consul solo, con un servicio de mentira, para entender qué hace exactamente. Al final lo conectamos con users-service y orders-service de verdad.

7.1 — Qué es Consul, en una frase

Consul es, él mismo, un servicio más que corre en tu sistema — un "directorio telefónico" al que los demás servicios llaman para registrarse ("aquí estoy, en esta dirección, en este puerto") y al que otros servicios preguntan ("¿dónde está el servicio X ahora mismo, y está sano?"). Nada mágico: por dentro, Consul expone su propia API HTTP normal y corriente — vamos a hablar con ella con curl, igual que hemos hablado con nuestros propios servicios.

7.2 — Arrancarlo solo, para verlo funcionar

No hace falta meterlo en el docker-compose.yml todavía. Un único comando lo levanta en modo desarrollo (no usar este modo en producción — sin persistencia ni seguridad, pero perfecto para aprender):

docker run -d --name consul-dev -p 8500:8500 -p 8600:8600/udp hashicorp/consul agent -dev -client=0.0.0.0

Abre http://localhost:8500 en el navegador — Consul trae una interfaz web propia donde vas a ver aparecer, en vivo, cada servicio que se registre. Déjala abierta en una pestaña mientras haces lo siguiente.

7.3 — Registrar un servicio a mano, con curl

Antes de tocar código Python, vamos a registrar un servicio "de mentira" directamente con curl, para ver exactamente qué información hace falta:

curl -X PUT http://localhost:8500/v1/agent/service/register \
  -H "Content-Type: application/json" \
  -d '{
    "Name": "users-service",
    "Address": "localhost",
    "Port": 8001,
    "Check": {
      "HTTP": "http://localhost:8001/users",
      "Interval": "10s"
    }
  }'

Esto le dice a Consul: "existe un servicio llamado users-service, en localhost:8001, y cada 10 segundos comprueba tú mismo si sigue vivo llamando a /users". Si tienes users-service del módulo 5 corriendo en local (fuera de Docker, con uvicorn main:app --port 8001), ese health check lo vas a ver pasar de verdad.

Ahora pregúntale a Consul quién está registrado y sano:

curl http://localhost:8500/v1/health/service/users-service?passing=true

Devuelve un JSON con la dirección, el puerto, y el estado del health check. Esto es la pieza que Docker Compose no te da gratis: docker-compose resuelve el nombre a una IP, pero no sabe (ni le importa) si el servicio detrás responde de verdad. Consul sí lo sabe, porque lo comprueba activamente.

Pruébalo tú mismo, en vivo: Para users-service (Ctrl+C si lo tienes corriendo suelto, o docker compose stop users-service si está en Docker) y repite la consulta de arriba a los pocos segundos — el health check falla, y Consul deja de devolver esa instancia como passing. Un servicio que solo mirase el resultado de passing=true nunca intentaría llamar a una instancia caída — eso es lo que gana un sistema real usando Consul en vez de Docker Compose a secas.

7.4 — Integrarlo en el sistema de los módulos 4-6

Para que users-service se registre solo al arrancar (en vez de hacerlo a mano con curl), se añade una llamada HTTP a Consul en el arranque de la aplicación:

users-service/main.py — añadir al principio 
import httpx
from fastapi import FastAPI

app = FastAPI(title="users-service")

@app.on_event("startup")
def register_with_consul():
    httpx.put(
        "http://consul:8500/v1/agent/service/register",
        json={
            "Name": "users-service",
            "Address": "users-service",
            "Port": 8001,
            "Check": {"HTTP": "http://users-service:8001/users", "Interval": "10s"},
        },
    )

# ... el resto de users-service/main.py sigue igual que en el módulo 5

Y orders-service, en vez de tener la dirección de users-service escrita a fuego (USERS_SERVICE_URL = "http://users-service:8001" del módulo 5), le pregunta a Consul cada vez:

orders-service/main.py — reemplaza USERS_SERVICE_URL fijo 
def find_users_service() -> str:
    resp = httpx.get("http://consul:8500/v1/health/service/users-service?passing=true")
    instances = resp.json()
    if not instances:
        raise HTTPException(status_code=503, detail="users-service no disponible ahora mismo")
    service = instances[0]["Service"]
    return f"http://{service['Address']}:{service['Port']}"

# dentro de create_order(), en vez de USERS_SERVICE_URL fijo:
users_url = find_users_service()
resp = httpx.get(f"{users_url}/users/{order.user_id}", timeout=3.0)

Y en docker-compose.yml, se añade Consul como un servicio más:

docker-compose.yml — añadir 
  consul:
    image: hashicorp/consul:latest
    command: "agent -dev -client=0.0.0.0"
    ports:
      - "8500:8500"
La diferencia real, en una frase, para cerrar el módulo: Con Docker Compose a secas, orders-service siempre confía en que users-service está bien con solo resolver su nombre. Con Consul, orders-service pregunta activamente "¿está sano ahora mismo?" antes de llamar — y si la respuesta es que no, puede decidir qué hacer (esperar, avisar, usar otra instancia) en vez de estrellarse contra un servicio caído sin saberlo de antemano.
