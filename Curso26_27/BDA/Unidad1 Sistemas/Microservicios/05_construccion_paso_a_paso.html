5. Construcción paso a paso

Vamos a construir los tres servicios en orden: primero el más simple (users-service, sin dependencias de nadie), luego el que depende de él (orders-service), y por último el que los une de cara a fuera (gateway). Al Docker en sí ya lo conoces de otro de nuestros cursos — aquí nos centramos en cómo se usa para varios servicios que colaboran entre sí, que es la parte nueva.

Paso 1 — el servicio de usuarios

Este es el servicio más simple: no llama a nadie más, solo responde con datos que guarda en memoria.

users-service/main.py 
from fastapi import FastAPI, HTTPException

app = FastAPI(title="users-service")

# "Base de datos" en memoria -- suficiente para aprender el patrón.
# En un sistema real, cada microservicio tendría su propia BD de verdad
# (Postgres, por ejemplo), nunca compartida con otro servicio.
USERS = {
    1: {"id": 1, "name": "David"},
    2: {"id": 2, "name": "Marta"},
    3: {"id": 3, "name": "Ana"},
}

@app.get("/users")
def list_users():
    return list(USERS.values())

@app.get("/users/{user_id}")
def get_user(user_id: int):
    user = USERS.get(user_id)
    if not user:
        raise HTTPException(status_code=404, detail="Usuario no encontrado")
    return user
users-service/Dockerfile 
FROM python:3.12-slim
WORKDIR /app
RUN pip install fastapi uvicorn
COPY main.py .
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8001"]
Un detalle que se pasa por alto la primera vez: el host es 0.0.0.0, no 127.0.0.1. Dentro de un contenedor, 127.0.0.1 significa "solo accesible desde dentro de este mismo contenedor" — otros contenedores (como orders-service) no podrían llegar a él. 0.0.0.0 significa "escucha en cualquier interfaz de red", que es lo que hace falta para que otros servicios lo alcancen.

Paso 2 — el servicio de pedidos (la pieza importante de verdad)

orders-service no confía a ciegas en que el user_id que le mandan existe — se lo pregunta a users-service por HTTP, usando su nombre de servicio como si fuera un hostname normal (http://users-service:8001). Ese nombre lo resuelve automáticamente la red que crea docker-compose — es el service discovery del módulo 3 en acción.

orders-service/main.py 
import httpx
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI(title="orders-service")

ORDERS = []
NEXT_ID = 1
USERS_SERVICE_URL = "http://users-service:8001"  # nombre del servicio en docker-compose

class OrderIn(BaseModel):
    user_id: int
    item: str

@app.get("/orders")
def list_orders():
    return ORDERS

@app.post("/orders", status_code=201)
def create_order(order: OrderIn):
    global NEXT_ID

    # Llamada real a otro microservicio, por HTTP, igual que haría un navegador.
    # httpx es como "requests" pero soporta también llamadas asíncronas.
    resp = httpx.get(f"{USERS_SERVICE_URL}/users/{order.user_id}", timeout=3.0)
    if resp.status_code == 404:
        raise HTTPException(status_code=400, detail="Ese usuario no existe")
    resp.raise_for_status()  # lanza error si la respuesta es un fallo (5xx)
    user = resp.json()

    new_order = {"id": NEXT_ID, "user": user, "item": order.item}
    ORDERS.append(new_order)
    NEXT_ID += 1
    return new_order
orders-service/Dockerfile 
FROM python:3.12-slim
WORKDIR /app
RUN pip install fastapi uvicorn httpx pydantic
COPY main.py .
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8002"]
Por qué esto importa más de lo que parece: aquí acaba de aparecer el problema central de los microservicios que un monolito no tiene — timeout=3.0 existe porque esta llamada puede fallar o tardar. Si users-service estuviera caído, esta línea lanzaría una excepción de red. En un monolito, una llamada a otra parte del código nunca "falla por la red" — aquí sí, siempre. El módulo 6 lo demuestra en vivo.

Paso 3 — el gateway

El cliente nunca habla directamente con users-service ni con orders-service — solo con el gateway. El gateway mira la ruta que le piden y reenvía la petición al servicio correcto, devolviendo la respuesta tal cual.

gateway/main.py 
import httpx
from fastapi import FastAPI, Request, Response

app = FastAPI(title="gateway")

ROUTES = {
    "users":  "http://users-service:8001",
    "orders": "http://orders-service:8002",
}

@app.api_route("/{service}/{path:path}", methods=["GET", "POST"])
async def proxy(service: str, path: str, request: Request):
    base_url = ROUTES.get(service)
    if not base_url:
        return Response(content=f'{{"error":"servicio {service} desconocido"}}',
                         status_code=404, media_type="application/json")

    target_url = f"{base_url}/{service}/{path}" if path else f"{base_url}/{service}"
    body = await request.body()

    async with httpx.AsyncClient() as client:
        resp = await client.request(
            request.method, target_url, content=body,
            params=request.query_params, timeout=5.0,
        )
    return Response(content=resp.content, status_code=resp.status_code,
                     media_type=resp.headers.get("content-type"))
gateway/Dockerfile 
FROM python:3.12-slim
WORKDIR /app
RUN pip install fastapi uvicorn httpx
COPY main.py .
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

Uniéndolo todo: docker-compose

Este es el fichero que convierte tres carpetas sueltas en un sistema — levanta los tres servicios en la misma red, con nombres resolubles entre ellos (el users-service:8001 de los ficheros de arriba existe gracias a esto).

docker-compose.yml (en la raíz, junto a las 3 carpetas) 
services:
  users-service:
    build: ./users-service
    ports:
      - "8001:8001"

  orders-service:
    build: ./orders-service
    ports:
      - "8002:8002"
    depends_on:
      - users-service

  gateway:
    build: ./gateway
    ports:
      - "8000:8000"
    depends_on:
      - users-service
      - orders-service
¿Qué hace depends_on? Le dice a Docker en qué orden arrancar los contenedores — orders-service no arranca hasta que users-service ha empezado. Ojo: esto NO garantiza que users-service ya esté listo para recibir peticiones, solo que el contenedor ha arrancado. Es una limitación real de docker-compose simple; en sistemas de verdad se añaden comprobaciones de salud (health checks) para esto — lo dejamos fuera hoy para no complicar el primer ejemplo.

Para levantarlo todo:

docker compose up --build
