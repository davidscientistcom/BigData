1. Por qué existen los microservicios

Antes de tocar la palabra "microservicio", hablemos de lo que ya conoces: cuando escribes un programa en Python, normalmente todo vive en un solo proceso. Un proceso es, literalmente, un programa en ejecución con su propia memoria — cuando ejecutas python app.py, el sistema operativo arranca un proceso, y todo lo que ese script hace (leer un fichero, calcular algo, responder a un usuario) pasa por ahí dentro.

Una aplicación tradicional — un monolito — es exactamente eso a mayor escala: un único proceso (o varias copias idénticas del mismo proceso) que contiene todo el negocio. Si es una tienda online: la gestión de usuarios, el catálogo, los pedidos, los pagos, las notificaciones — todo vive junto, en el mismo código fuente, se despliega junto, se reinicia junto.

Y esto no es un error de diseño. Para la inmensa mayoría de proyectos, es la opción correcta: es más simple de escribir, de depurar (todo el flujo de una petición pasa por el mismo proceso, con una sola pila de llamadas) y de desplegar (subes una cosa, no diez).

El problema aparece cuando el monolito crece

El dolor no es "es viejo" o "es feo" — son cuatro problemas concretos y medibles:

  • Desplegar da miedo. Si tocas el módulo de notificaciones y metes un bug, tumbas también pagos — es el mismo proceso, un fallo no controlado (una excepción que mata el proceso, una fuga de memoria) afecta a todo lo que vive dentro.
  • Escalar es todo o nada. Escalar significa "levantar más copias para aguantar más tráfico". Si solo el módulo de pedidos recibe mucho tráfico (Black Friday), no puedes escalar solo esa parte — tienes que levantar copias enteras de todo el monolito, gastando recursos en partes que no lo necesitan.
  • Equipos grandes se pisan. Diez personas tocando el mismo repositorio de código significa conflictos de Git constantes, y un único pipeline de despliegue que todo el mundo tiene que esperar — si alguien rompe algo, nadie más puede desplegar hasta que se arregle.
  • Estás atado a una sola tecnología por proceso. Todo lo que vive en el mismo proceso normalmente tiene que estar en el mismo lenguaje y las mismas dependencias. Si el módulo de recomendaciones necesitaría una librería de Python que choca con una versión que usa el resto del sistema, no hay una forma limpia de mezclar dentro de un único proceso.

La respuesta: partir el proceso, no solo el código

Los microservicios resuelven esto partiendo esa única aplicación en varios programas independientes — no solo carpetas distintas dentro del mismo proceso, sino procesos de verdad separados, cada uno con:

  • Una sola responsabilidad (ej. "todo lo de usuarios", nada más).
  • Su propio ciclo de vida — se puede reiniciar, actualizar o escalar sin tocar los demás.
  • Su propia base de datos, si la necesita — nunca compartida directamente con otro servicio.
¿Por qué cada servicio necesita su propia base de datos? Porque si dos microservicios leen y escriben en las mismas tablas, has recreado el acoplamiento que querías eliminar — solo que ahora vive en la base de datos en vez de en el código. El equipo de pedidos no podría cambiar una columna sin arriesgarse a romper al equipo de usuarios, que también la usa. Cada servicio debe ser el único dueño de sus propios datos; si otro servicio necesita esa información, la pide por su API (como hace orders-service con users-service más adelante en este curso) — nunca leyendo su base de datos por detrás.

Como ahora son procesos distintos (posiblemente en máquinas distintas), ya no pueden "llamarse" entre ellos como funciones de Python normales — tienen que hablar por la red. De eso trata el resto del curso.

La trampa que hay que evitar desde el primer día: No se montan microservicios porque "es lo moderno" o porque las empresas grandes lo hacen. Se montan cuando el dolor de arriba es real y medible. Empezar un proyecto nuevo y pequeño directamente en microservicios suele ser un error: añades toda la complejidad de la red (una llamada puede fallar a medias, hay que pensar en latencia, hay que mantener varias bases de datos consistentes entre sí) sin tener todavía el problema de escala/equipo que lo justifica. Un monolito bien organizado por dentro (módulos separados dentro del mismo proceso) aguanta mucho antes de necesitar este salto.
