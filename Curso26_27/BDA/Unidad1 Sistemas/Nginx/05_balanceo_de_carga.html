Balanceo de Carga & Alta Disponibilidad

El bloque upstream, algoritmos de distribución (Round-Robin, Least-Connections, IP-Hash), balanceo ponderado para clústeres de GPUs heterogéneas y conmutación automática ante fallos (Failover).

1. Escalabilidad Horizontal y el Bloque `upstream`

En proyectos de Big Data e Inteligencia Artificial, un único servidor de inferencia (por ejemplo FastAPI ejecutando un modelo PyTorch o TensorFlow) tiene un límite de capacidad física. La escalabilidad horizontal consiste en desplegar múltiples réplicas de la aplicación y colocar a NGINX como distribuidor de tráfico inteligente:

Distribución de Tráfico con el Bloque upstream

NGINX recibe en un único punto y reparte peticiones entre los nodos del clúster

El bloque upstream se define dentro del contexto http y crea una abstracción de red:

nginx • Definición básica de Upstream
# 1. Definir el grupo de servidores dentro de http {}
upstream backend_cluster {
    server 127.0.0.1:8001;
    server 127.0.0.1:8002;
    server 127.0.0.1:8003;
}

server {
    listen 80;
    server_name api.ia.local;

    location / {
        # 2. Apuntar al nombre simbólico del upstream
        proxy_pass http://backend_cluster;
        proxy_set_header Host $host;
    }
}

2. Algoritmos de Distribución de Carga

NGINX soporta múltiples algoritmos para decidir a qué servidor enviar cada nueva petición:

Algoritmo Directiva Mecanismo de Selección Mejor Caso de Uso
Round Robin (Por defecto) Cíclico secuencial (1 → 2 → 3 → 1...). Reparto equitativo. Backends con hardware idéntico y peticiones con tiempo de respuesta uniforme.
Least Connections least_conn; Elige el servidor con menor número de conexiones activas en ese instante. Esencial en IA: Cuando algunas peticiones tardan 50ms y otras tardan 4 segundos (inferencias complejas).
IP Hash ip_hash; Calcula un hash a partir de la IP del cliente IPv4 para enviarlo siempre al mismo backend. Persistencia de sesión (Sticky Sessions) cuando la app guarda datos en memoria local sin Redis.
Generic Hash hash $key [consistent]; Calcula el hash sobre cualquier variable (ej. hash $request_uri;). Maximizar ratio de aciertos de caché en microservicios deterministas.

3. Balanceo Ponderado (`weight`) para Clústeres Heterogéneos

En centros de datos reales, los servidores no siempre son iguales. Podemos tener máquinas con GPUs de alta potencia junto a máquinas auxiliares. El parámetro weight (peso) permite asignar proporcionalmente más tráfico a los servidores más potentes:

nginx • Pesos según capacidad de hardware
upstream ml_inference_pool {
    # Servidor 1: Servidor con Nvidia A100 (recibe el 50% de las peticiones)
    server 10.0.1.10:8000 weight=3;

    # Servidor 2: Servidor con Nvidia T4 (recibe el 33% de las peticiones)
    server 10.0.1.11:8000 weight=2;

    # Servidor 3: Servidor estándar con CPU (recibe el 17% de las peticiones)
    server 10.0.1.12:8000 weight=1;
}

4. Detección Pasiva de Caídas y Conmutación por Error (Failover)

NGINX comprueba activamente el estado de los backends. Si una réplica de FastAPI falla o se apaga, NGINX lo detecta de forma transparente sin que el usuario reciba un error:

nginx • Failover y Servidores Backup
upstream robust_backend {
    # max_fails: número de fallos consecutivos antes de marcarlo como muerto
    # fail_timeout: tiempo que permanecerá marcado como inactivo antes de reintentar
    server 10.0.1.10:8000 max_fails=3 fail_timeout=30s;
    server 10.0.1.11:8000 max_fails=3 fail_timeout=30s;

    # Servidor de respaldo (Hot Standby):
    # NGINX NUNCA le enviará tráfico a menos que los dos anteriores hayan caído
    server 10.0.1.12:8000 backup;

    # Servidor en mantenimiento manual (no recibirá tráfico jamás):
    server 10.0.1.13:8000 down;
}
💡

Reintento Inmediato con `proxy_next_upstream`

Si combinas el upstream con proxy_next_upstream error timeout http_502 http_503; dentro de location, si un backend responde con error 502 Bad Gateway, NGINX reintenta la petición instantáneamente en el siguiente backend disponible antes de devolverle la respuesta al cliente. El usuario nunca llega a ver el error.

5. Optimización Crítica: Conexiones Persistentes (`keepalive`)

Por defecto, NGINX abre una nueva conexión TCP hacia el backend para cada petición HTTP y la cierra inmediatamente al recibir la respuesta. Abrir y cerrar sockets TCP constantemente genera una penalización severa de CPU y latencia (TCP Handshake Overhead):

nginx • Keepalive de alto rendimiento con el backend
upstream fast_api_pool {
    server 127.0.0.1:8001;
    server 127.0.0.1:8002;

    # Mantener un pool de hasta 32 conexiones TCP abiertas y listas en caché
    keepalive 32;
}

server {
    listen 80;

    location /api/ {
        proxy_pass http://fast_api_pool;

        # OBLIGATORIO para que keepalive funcione con el backend:
        proxy_http_version 1.1;
        proxy_set_header Connection "";
    }
}
