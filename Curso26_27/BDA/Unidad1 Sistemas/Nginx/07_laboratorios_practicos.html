Laboratorio 01

Servidor Web Estático con Gzip y Página 404 Personalizada

Objetivo: Configurar NGINX para servir una web estática con compresión Gzip en tiempo real, manejo de caché para recursos estáticos y redirección interna segura a una página de error 404 personalizada sin revelar información del servidor.

1
Estructura de Directorios del Laboratorio

Crea la carpeta de trabajo en tu máquina o máquina virtual:

bash • Preparación de entorno
mkdir -p ~/lab_nginx/lab01/{html,conf}
cd ~/lab_nginx/lab01
2
Crear el archivo de configuración de NGINX

Guarda el siguiente contenido en conf/static_site.conf:

nginx • conf/static_site.conf
server {
    listen 8080;
    server_name localhost;
    root /var/www/lab01/html;
    index index.html;

    # Compresión Gzip dinámica
    gzip on;
    gzip_types text/plain text/css application/json application/javascript image/svg+xml;
    gzip_min_length 256;
    gzip_comp_level 6;
    gzip_vary on;

    # Ocultar cabeceras de versión del servidor
    server_tokens off;

    # Enrutamiento principal
    location / {
        try_files $uri $uri/ =404;
    }

    # Caché agresiva para assets
    location ~* \.(css|js|svg)$ {
        expires 7d;
        add_header Cache-Control "public, no-transform";
    }

    # Página de error 404 personalizada y protegida
    error_page 404 /404.html;
    location = /404.html {
        internal;
    }
}
3
Crear los archivos HTML y CSS de prueba

Laboratorio 02

Reverse Proxy para FastAPI con Inyección de IP Real del Cliente

Objetivo: Levantar un microservicio en Python FastAPI en el puerto local 8000 y configurarle un Reverse Proxy NGINX en el puerto 8080 que inyecte las cabeceras X-Real-IP y X-Forwarded-For, demostrando cómo el backend recupera la identidad real del visitante.

1
Código de la API en Python (FastAPI)

Crea el archivo backend.py:

python • backend.py
from fastapi import FastAPI, Request
import uvicorn

app = FastAPI(title="Servicio de Inferencia IA")

@app.get("/api/info")
def get_client_info(request: Request):
    return {
        "socket_direct_ip": request.client.host,
        "x_real_ip_header": request.headers.get("x-real-ip", "NO INYECTADA"),
        "x_forwarded_for": request.headers.get("x-forwarded-for", "NO INYECTADA"),
        "host_header": request.headers.get("host", "NO INYECTADA"),
        "status": "online"
    }

@app.get("/api/predict")
def predict():
    return {"prediction": "clase_positiva", "confidence": 0.985}

if __name__ == "__main__":
    # Escucha SOLO en localhost para impedir acceso directo desde fuera
    uvicorn.run(app, host="127.0.0.1", port=8000)
2
Configuración de NGINX Reverse Proxy

Guarda el siguiente bloque en conf/reverse_proxy.conf:

nginx • conf/reverse_proxy.conf
server {
    listen 8080;
    server_name localhost;

    # Enrutar todas las peticiones que comiencen por /api hacia Uvicorn
    location /api/ {
        proxy_pass http://127.0.0.1:8000;

        # INYECCIÓN CRÍTICA DE IDENTIDAD
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # Optimización de conexión persistente
        proxy_http_version 1.1;
        proxy_set_header Connection "";
    }
}

# 2. En otra terminal, consulta a través del Reverse Proxy NGINX:

Laboratorio 03

Clúster de Balanceo de Carga con Detección de Caídas (Failover)

Objetivo: Levantar 3 servidores de backend concurrentes simulados en Python (puertos 8001, 8002 y 8003). Configurar NGINX con balanceo ponderado y servidor de respaldo (backup). Ejecutar un script de prueba que mata un servidor en vivo y comprobar que el 100% de las peticiones subsiguientes siguen respondiendo sin un solo error.

1
Servidor de Backend Simulado Multipuerto

Guarda el siguiente script en cluster_nodes.py:

python • cluster_nodes.py
import sys
from http.server import HTTPServer, BaseHTTPRequestHandler
import json

class NodeHandler(BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.send_header('Content-Type', 'application/json')
        self.end_headers()
        response = {
            "node_port": self.server.server_port,
            "message": f"Respuesta generada con éxito por el Nodo en puerto {self.server.server_port}"
        }
        self.wfile.write(json.dumps(response).encode('utf-8'))

    def log_message(self, format, *args):
        # Log simplificado
        print(f"[{self.server.server_port}] Petición atendida desde NGINX")

if __name__ == '__main__':
    port = int(sys.argv[1]) if len(sys.argv) > 1 else 8001
    server = HTTPServer(('127.0.0.1', port), NodeHandler)
    print(f"Nodo activo y escuchando en http://127.0.0.1:{port}")
    try:
        server.serve_forever()
    except KeyboardInterrupt:
        print(f"\nNodo {port} detenido.")
2
Configuración del Upstream en NGINX con Failover

Guarda en conf/load_balancer.conf:

nginx • conf/load_balancer.conf
upstream ai_cluster {
    # Algoritmo: conexión más desocupada
    least_conn;

    # Nodo 1: Peso 2 (procesará el doble de carga)
    server 127.0.0.1:8001 weight=2 max_fails=2 fail_timeout=10s;

    # Nodo 2: Nodo estándar
    server 127.0.0.1:8002 weight=1 max_fails=2 fail_timeout=10s;

    # Nodo 3: Servidor de RESPALDO (Hot Standby)
    # Solo recibirá peticiones si el Nodo 1 y el Nodo 2 se caen simultáneamente
    server 127.0.0.1:8003 backup;
}

server {
    listen 8080;
    server_name localhost;

    location / {
        proxy_pass http://ai_cluster;
        proxy_set_header Host $host;

        # Si un nodo falla, salta inmediatamente al siguiente sin error al cliente
        proxy_next_upstream error timeout http_502 http_503;
        proxy_connect_timeout 2s;
    }
}
3
Script Automatizado de Verificación y Simulación de Caída

Guarda y ejecuta test_failover.py para ver el comportamiento en vivo:

python • test_failover.py
import urllib.request
import json

print("=== FASE 1: Enviando 10 peticiones con los nodos 8001 y 8002 activos ===")
for i in range(1, 11):

Laboratorio 04

Rate Limiting en Vivo: Prueba de Saturación y Rechazo HTTP 429

Objetivo: Blindar una ruta de inferencia de IA limitando el tráfico a un máximo de 5 peticiones por segundo con una ráfaga (burst) permitida de 5. Ejecutar un script de prueba de carga concurrente que bombardea el endpoint y observar cómo NGINX devuelve 200 OK en las permitidas y corta inmediatamente con 429 Too Many Requests el tráfico abusivo.

1
Configuración de Rate Limiting en NGINX

Guarda el siguiente bloque en conf/ratelimit.conf:

nginx • conf/ratelimit.conf
# Definir zona de memoria para 160.000 IPs a 5 peticiones/segundo
limit_req_zone $binary_remote_addr zone=ai_limit:10m rate=5r/s;
limit_req_status 429;

server {
    listen 8080;
    server_name localhost;

    # Endpoint protegido con Rate Limiting
    location /api/infer/ {
        limit_req zone=ai_limit burst=5 nodelay;

        # Simulación de respuesta rápida en memoria
        default_type application/json;
        return 200 '{"status":"success","data":"Inferencia de modelo generada exitosamente"}\n';
    }

    # Endpoint libre sin limitación (ej. health checks)
    location /health {
        default_type application/json;
        return 200 '{"status":"ok"}\n';
    }
}
2
Script de Prueba de Saturación Concurrente

Guarda y ejecuta test_ratelimit.py:

python • test_ratelimit.py
import concurrent.futures
import urllib.request
import urllib.error

URL = "http://localhost:8080/api/infer/"
TOTAL_REQUESTS = 20

def send_request(req_id):
    try:
        with urllib.request.urlopen(URL) as response:
            return req_id, response.getcode(), "Aceptada (200 OK)"
    except urllib.error.HTTPError as e:
        return req_id, e.code, "Bloqueada por Rate Limiting (429)"
    except Exception as e:
        return req_id, 0, str(e)

print(f"Lanzando {TOTAL_REQUESTS} peticiones simultáneas contra {URL}...\n")

with concurrent.futures.ThreadPoolExecutor(max_workers=10) as executor:
    results = list(executor.map(send_request, range(1, TOTAL_REQUESTS + 1)))

ok_count = sum(1 for _, code, _ in results if code == 200)
blocked_count = sum(1 for _, code, _ in results if code == 429)

for req_id, code, msg in sorted(results, key=lambda x: x[0]):
    symbol = "✅" if code == 200 else "🛑"
    print(f"{symbol} Petición #{req_id:02d} -> HTTP {code}: {msg}")

print(f"\n==========================================")
print(f"Peticiones Procesadas con Éxito (200): {ok_count}")
print(f"Peticiones Mitigadas / Bloqueadas (429): {blocked_count}")
print(f"==========================================")
Laboratorio 05

Terminación SSL/HTTPS con Certificado Autofirmado y Redirección 301

Objetivo: Generar un certificado de seguridad X.509 y clave privada con openssl, configurar NGINX con terminación HTTPS en el puerto 8443 y comprobar la redirección permanente 301 desde el puerto HTTP 8080.

1
Generación de Certificado y Clave Privada
bash • Creación de certificados con openssl
mkdir -p certs

openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout certs/nginx.key \
  -out certs/nginx.crt \
  -subj "/C=ES/ST=Alicante/L=SanVicente/O=IES/CN=localhost"

chmod 600 certs/nginx.key
2
Configuración Dual HTTP/HTTPS en NGINX
nginx • conf/ssl_redirect.conf
# Servidor 1: HTTP Inseguro -> Redirección forzada
server {
    listen 8080;
    server_name localhost;
    return 301 https://$host:8443$request_uri;
}

# Servidor 2: HTTPS Seguro
server {
    listen 8443 ssl;
    server_name localhost;

    ssl_certificate /ruta/absoluta/certs/nginx.crt;
    ssl_certificate_key /ruta/absoluta/certs/nginx.key;

    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5;

    location / {
        default_type text/html;
        return 200 '<h1 style="color:#10b981;">¡Conexión HTTPS Encriptada con NGINX Exitosa!</h1>\n';
    }
}
3
Comprobación de Redirección y Cifrado
bash • Verificación con curl
# 1. Comprobar que el puerto 8080 redirige con HTTP 301
curl -I http://localhost:8080/test
# Salida esperada: HTTP/1.1 301 Moved Permanently
# Location: https://localhost:8443/test

# 2. Comprobar la conexión segura HTTPS (-k omite la advertencia de certificado autofirmado)
curl -k -I https://localhost:8443/
# Salida esperada: HTTP/1.1 200 OK con conexión encriptada TLS
Laboratorio 06

Despliegue Multi-Contenedor Completo con Docker Compose (API Gateway)

Objetivo: Orquestar un entorno completo de microservicios mediante Docker Compose donde NGINX actúa como único punto de entrada público (API Gateway), enrutando el frontend estático en / y balanceando la API de FastAPI entre dos contenedores en red privada aislada.

1
Estructura del Proyecto Docker
bash • Árbol de archivos
docker_compose_lab/
├── docker-compose.yml
├── nginx/
│   └── default.conf
├── backend/
│   ├── Dockerfile
│   ├── requirements.txt
│   └── main.py
└── frontend/
    └── index.html
2
Archivo docker-compose.yml
yaml • docker-compose.yml
version: '3.8'

services:
  # RECURSO ÚNICO EXPUESTO A INTERNET
  gateway:
    image: nginx:alpine
    container_name: nginx_api_gateway
    ports:
      - "80:80"
    volumes:
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
      - ./frontend:/usr/share/nginx/html:ro
    depends_on:
      - api_node_1
      - api_node_2
    networks:
      - internal_net

  # NODO 1 DE INFERENCIA (RED PRIVADA, PUERTO CERRADO AL EXTERIOR)
  api_node_1:
    build: ./backend
    container_name: api_replica_1
    environment:
      - NODE_NAME=Replica-Alpha
    expose:
      - "8000"
    networks:
      - internal_net

  # NODO 2 DE INFERENCIA (RED PRIVADA, PUERTO CERRADO AL EXTERIOR)
  api_node_2:
    build: ./backend
    container_name: api_replica_2
    environment:
      - NODE_NAME=Replica-Beta
    expose:
      - "8000"
    networks:
      - internal_net

networks:
  internal_net:
    driver: bridge
3
Configuración del API Gateway (nginx/default.conf)
nginx • nginx/default.conf
upstream backend_nodes {
    # Resolución DNS nativa interna de Docker
    server api_node_1:8000;
    server api_node_2:8000;
}

server {
    listen 80;
    server_name localhost;

    # 1. Frontend estático
    location / {
        root /usr/share/nginx/html;
        index index.html;
        try_files $uri $uri/ /index.html;
    }

    # 2. Reverse Proxy balanceado hacia FastAPI
    location /api/ {
        proxy_pass http://backend_nodes;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
