Anatomía de Configuración & Enrutamiento

Estructura jerárquica de contextos, directivas esenciales de producción y el algoritmo de coincidencia y precedencia de location.

1. Jerarquía de Contextos (Context Hierarchy)

El archivo de configuración de NGINX se organiza de forma arbórea en bloques anidados denominados Contextos. Cada contexto define el alcance de las directivas que contiene, aplicando reglas de herencia desde los niveles superiores hacia los inferiores:

Árbol de Contextos en NGINX

Las directivas del contexto superior se heredan en los hijos, salvo que se sobrescriban explícitamente

1.1 Desglose de Contextos Principales

  • main: Contexto raíz (sin llaves). Define la gestión del proceso global, usuario de ejecución (user www-data;), número de procesos worker y ubicación de logs de arranque.
  • events: Ajusta los parámetros de red a bajo nivel. La directiva worker_connections 1024; define cuántos sockets simultáneos puede gestionar cada worker.
  • http: Configura todo el comportamiento HTTP/HTTPS. Contiene directivas que aplican a todos los sitios web (compresión gzip, tipos MIME, logs de acceso, cabeceras globales).
  • server: Representa un Virtual Host (servidor virtual). Se activa en función de la IP, puerto de escucha (listen 80;) y nombre de dominio (server_name midominio.com;).
  • location: Se encuentra dentro de server y gestiona el enrutamiento de peticiones basándose en la URI solicitada (ej. /api, /static/ o /).
  • upstream: Define un clúster de servidores de backend para balancear tráfico o actuar como proxy.

2. Reglas Sintácticas Fundamentales

La configuración de NGINX es rigurosa. Un error de sintaxis impedirá que el servicio arranque:

  • El punto y coma obligatorio: Cada directiva simple DEBE finalizar con un punto y coma ;. Olvidarlo es el error número 1 de configuración.
  • Llaves para bloques: Los contextos se delimitan estrictamente con { y }.
  • Comentarios: Cualquier texto precedido por una almohadilla # es ignorado por el analizador sintáctico.
  • Unidades de medida: NGINX comprende sufijos amigables como k/K (Kilobytes), m/M (Megabytes), ms (milisegundos), s (segundos), m (minutos) o d (días). Ej: client_max_body_size 50M;.

3. Algoritmo de Precedencia y Coincidencia de `location`

Cuando llega una petición HTTP (por ejemplo GET /api/v1/predict), NGINX analiza todos los bloques location definidos dentro del server correspondiente. El orden en el que están escritos en el archivo NO siempre determina cuál se ejecuta. NGINX sigue un algoritmo de prioridad estricto:

Prioridad Modificador Tipo de Coincidencia Comportamiento y Regla de Parada
1 (Máxima) = /ruta Coincidencia Exacta Si la URI es exactamente igual, se detiene la búsqueda de inmediato y se ejecuta este bloque. Cero ambigüedad.
2 ^~ /ruta Prefijo con Parada Si coincide con el prefijo más largo, NGINX NO evalúa ninguna expresión regular posterior. Detiene la búsqueda.
3 ~ regex Expresión Regular (Case Sensitive) Sensible a mayúsculas y minúsculas. Se evalúan en el orden en el que aparecen escritas en el archivo. La primera que coincide, gana.
3 ~* regex Expresión Regular (Case Insensitive) Insensible a mayúsculas/minúsculas (ej. \.(jpg|png|gif)$). Comparte prioridad con ~ según orden de aparición.
4 (Fallback) /ruta (sin modificador) Prefijo Convencional Busca el prefijo más largo que coincida. Si no coincide ninguna regex en el paso 3, se aplica este prefijo más largo almacenado.

3.1 Caso Práctico: ¿Qué bloque gana ante cada URL?

Considera la siguiente configuración con múltiples bloques location:

nginx • Ejemplo de precedencia
server {
    listen 80;
    server_name test.local;

    # Bloque A: Coincidencia exacta
    location = /login {
        return 200 "Bloque A: Login Exacto\n";
    }

    # Bloque B: Prefijo con parada de regex
    location ^~ /static/ {
        return 200 "Bloque B: Archivo Estático con ^~\n";
    }

    # Bloque C: Expresión regular (imágenes)
    location ~* \.(png|jpg|jpeg)$ {
        return 200 "Bloque C: Imagen por Regex\n";
    }

    # Bloque D: Prefijo largo convencional
    location /api/v1/ {
        return 200 "Bloque D: API Prefijo Largo\n";
    }

    # Bloque E: Fallback raíz
    location / {
        return 200 "Bloque E: Fallback Raíz\n";
    }
}
Petición URI entrante Bloque Ganador Explicación Técnica
/login Bloque A Coincidencia exacta = (Prioridad 1). Se detiene de inmediato.
/login?redirect=dashboard Bloque A Los parámetros de query string (?redirect=...) se descartan al evaluar location; la URI pura es /login.
/login/two-factor Bloque E No coincide exactamente con = /login, por lo que cae en el fallback /.
/static/avatar.png Bloque B Aunque .png coincide con la regex del Bloque C, el modificador ^~ del Bloque B anula la evaluación de expresiones regulares.
/uploads/avatar.PNG Bloque C No coincide con ^~, se evalúan las regex y ~* coincide ignorando mayúsculas.
/api/v1/users Bloque D Prefijo más largo convencional. Ninguna regex coincide, por lo que gana sobre el Bloque E (/).

4. Variables de Entorno y Contexto de Petición

NGINX inyecta decenas de variables mágicas que permiten tomar decisiones dinámicas, registrar información en logs o reenviar cabeceras al backend:

Variables de Conexión & Cliente
  • $remote_addr: Dirección IP real del cliente TCP.
  • $remote_port: Puerto efímero del cliente.
  • $scheme: Protocolo utilizado (http o https).
  • $request_method: Método HTTP (GET, POST, etc.).
Variables de URI & Cabeceras
  • $host: Dominio solicitado en la cabecera Host.
  • $request_uri: La URI completa original con parámetros (ej. /api/item?id=12).
  • $uri: La URI actual normalizada (sin parámetros).
  • $http_user_agent: Valor de la cabecera User-Agent del cliente.
