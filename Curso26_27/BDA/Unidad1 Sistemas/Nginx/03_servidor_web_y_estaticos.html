Servidor Web & Archivos Estáticos

Servir contenido a velocidad nativa con sendfile, la diferencia crítica entre root y alias, enrutamiento SPA con try_files y compresión dinámica Gzip.

1. El Gran Dilema: `root` vs `alias`

Una de las fuentes de errores 404 Not Found más repetidas en el desarrollo web es la confusión entre las directivas root y alias. Ambas indican en qué carpeta física del disco duro se encuentran los archivos, pero construyen la ruta final de manera totalmente diferente:

La Directiva `root` (Concatenación Pura)

NGINX toma la ruta definida en root y le añade la URI completa que pidió el cliente: 

location /static/ {
    root /var/www/app;
}

# Petición entrante:
# GET /static/css/style.css
#
# Ruta física que busca NGINX en disco:
# /var/www/app/static/css/style.css
# (Concatena /var/www/app + /static/css/style.css)

La Directiva `alias` (Sustitución de Prefijo)

NGINX reemplaza la parte coincidente de la location por la ruta del alias: 

location /static/ {
    alias /data/recursos/;
}

# Petición entrante:
# GET /static/css/style.css
#
# Ruta física que busca NGINX en disco:
# /data/recursos/css/style.css
# (Sustituye /static/ por /data/recursos/)
⚡

Regla Crítica con `alias`: Cuidado con la barra final `/`

Si defines location /static/ con una barra al final, la ruta en alias DEBE terminar también con una barra al final (alias /data/recursos/;). Si olvidas la barra, NGINX intentará concatenar cadenas de texto sin separador de carpetas (buscando /data/recursoscss/style.css), provocando errores 404 inesperados.

2. Enrutamiento Moderno de SPAs con `try_files`

En aplicaciones web modernas (Single Page Applications como React, Vue, Angular o dashboards de IA como Streamlit/Vite), el enrutamiento lo gestiona JavaScript en el navegador mediante el History API (por ejemplo midominio.com/dashboard/analytics).

Si el usuario recarga la página en esa URL, el servidor web intentará buscar un archivo físico llamado /analytics que no existe en disco. Para solucionar esto se utiliza try_files:

nginx • Configuración para SPA y Dashboard
server {
    listen 80;
    server_name dashboard.ia.local;
    root /var/www/dashboard/dist;
    index index.html;

    location / {
        # 1. Comprueba si existe el archivo exacto ($uri)
        # 2. Comprueba si existe una carpeta ($uri/)
        # 3. Si no existe ninguno, entrega /index.html (para que React/Vue enruten)
        try_files $uri $uri/ /index.html;
    }

    # Bloque de assets con expiración agresiva de caché
    location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|woff2)$ {
        expires 1y;
        add_header Cache-Control "public, no-transform, immutable";
        access_log off;
    }
}

3. Aceleración con Kernel Zero-Copy: `sendfile` y `tcp_nopush`

Tradicionalmente, para enviar un archivo desde el disco hacia la tarjeta de red, el sistema operativo leía los datos del disco al espacio del kernel, los copiaba al espacio de memoria del usuario (NGINX), y NGINX los volvía a copiar al socket del kernel:

nginx • Optimizaciones en el contexto http
http {
    # 1. Zero-Copy: El kernel transfiere datos directamente del disco a la tarjeta de red
    #    sin pasar por la memoria de la aplicación. CPU prácticamente al 0%.
    sendfile on;

    # 2. Envía cabeceras HTTP y el inicio del fichero en un único paquete TCP
    tcp_nopush on;

    # 3. Desactiva el algoritmo de Nagle para enviar respuestas inmediatas sin latencia
    tcp_nodelay on;

    # 4. Mantiene la conexión TCP abierta durante 65 segundos para reutilizarla
    keepalive_timeout 65;
}

4. Compresión Dinámica con Gzip

El código HTML, CSS, JavaScript y las respuestas JSON de las APIs son texto plano altamente comprimible. Activar Gzip reduce el tamaño de transferencia entre un 70% y un 80%, mejorando radicalmente la velocidad percibida y el consumo de ancho de banda:

nginx • Configuración de compresión Gzip
# Activar motor Gzip
gzip on;

# Nivel de compresión: 1 (rápido, menos compresión) a 9 (máxima compresión, más CPU)
# El nivel 5 o 6 es el balance perfecto en producción:
gzip_comp_level 6;

# No comprimir archivos menores a 256 bytes (el overhead de gzip los haría más grandes)
gzip_min_length 256;

# Cabecera Vary: Accept-Encoding para que los proxies intermedios sepan qué versión cachear
gzip_vary on;

# Tipos MIME a comprimir (NUNCA incluyas jpg/png/mp4 porque ya están comprimidos)
gzip_types
    text/plain
    text/css
    text/xml
    application/json
    application/javascript
    application/xml
    image/svg+xml;

4.1 Cómo Verificar Gzip desde Terminal con `curl`

bash • Prueba de compresión
# Simular una petición de navegador anunciando soporte de compresión
curl -I -H "Accept-Encoding: gzip" http://localhost/style.css

# Si está funcionando correctamente, la respuesta incluirá:
# HTTP/1.1 200 OK
# Content-Type: text/css
# Content-Encoding: gzip    <--- ¡COMPRESIÓN ACTIVA!
# Vary: Accept-Encoding

5. Páginas de Error Personalizadas y Directiva `internal`

Mostrar los errores por defecto de NGINX revela la versión del servidor y ofrece una experiencia descuidada al usuario. NGINX permite definir páginas HTML elegantes para códigos 404, 500 o 502:

nginx • Gestión de páginas de error
server {
    listen 80;
    server_name portal.local;
    root /var/www/html;

    # Mapeo de errores a ficheros
    error_page 404 /custom_404.html;
    error_page 500 502 503 504 /custom_50x.html;

    # SEGURIDAD CRÍTICA: La directiva 'internal'
    # Impide que un usuario acceda escribiendo en el navegador:
    # http://portal.local/custom_404.html de forma directa
    location = /custom_404.html {
        internal;
    }

    location = /custom_50x.html {
        internal;
    }
}
