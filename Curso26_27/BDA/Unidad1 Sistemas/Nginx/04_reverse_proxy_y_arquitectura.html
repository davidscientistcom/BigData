Reverse Proxy & Arquitectura de Backend

Por qué los servidores de aplicación (FastAPI, Flask, Express) nunca deben exponerse directamente, la regla de la barra final en proxy_pass, cabeceras de identidad del cliente y streaming no bloqueante para IA.

1. Forward Proxy vs Reverse Proxy

El término Proxy significa intermediario o representante. En redes informáticas existen dos variantes fundamentales según la entidad a la que protegen:

👤

Forward Proxy (Protege al Cliente)

Se coloca frente a los clientes (usuarios). El cliente configura su navegador para pasar por el proxy, el cual oculta la identidad del cliente ante los servidores de Internet.

Ejemplo clásico: Una VPN corporativa, Tor o un proxy de filtrado en un instituto.

🛡️

Reverse Proxy (Protege al Servidor)

Se coloca frente a los servidores de la empresa. El cliente exterior cree que habla con el servidor final, pero NGINX intercepta la petición y decide internamente a qué aplicación delegarla.

Ejemplo clásico: NGINX recibiendo peticiones en el puerto 80/443 y enrutándolas hacia Uvicorn en el puerto 8000.

2. ¿Por qué FastAPI/Uvicorn NUNCA deben exponerse directamente?

En tutoriales de desarrollo es común ver uvicorn main:app --host 0.0.0.0 --port 8000 abierto directamente a Internet. En un entorno de producción o pruebas reales, esto supone graves riesgos:

  • Vulnerabilidad ante ataques Slowloris: Un atacante puede abrir cientos de conexiones enviando cabeceras a 1 byte por segundo. Uvicorn mantiene sockets abiertos en Python, agotando los recursos de la máquina y dejando el servicio inaccesible. NGINX, gracias a su arquitectura asíncrona, absorbe estos ataques sin inmutarse.
  • Sobrecarga Criptográfica: Delegar la negociación de claves TLS (HTTPS) y la descompresión al intérprete de Python ralentiza drásticamente el rendimiento de cálculo de los modelos de IA. NGINX realiza la descarga de SSL en C a nivel de kernel.
  • Aislamiento de Red: En contenedores Docker, los backends deben configurarse con expose: 8000 (accesible únicamente dentro de la red interna de contenedores) y nunca con ports: 8000:8000. NGINX es el único contenedor expuesto al exterior.

3. La Directiva `proxy_pass` y el Misterio de la Barra Final

Una de las directivas más utilizadas y a la vez más incomprendidas es proxy_pass. La presencia o ausencia de una barra diagonal / al final de la URL cambia radicalmente cómo NGINX reescribe la petición antes de enviársela al backend:

Configuración NGINX Petición del Cliente Petición que recibe FastAPI Explicación
location /api/ {
  proxy_pass http://127.0.0.1:8000;
}
Sin barra al final de la URL 		GET /api/v1/users GET /api/v1/users Paso directo sin alteración: NGINX añade la URI original completa al backend tal cual fue solicitada.
location /api/ {
  proxy_pass http://127.0.0.1:8000/;
}
CON barra final (URI de sustitución) 		GET /api/v1/users GET /v1/users Reescritura de prefijo: NGINX elimina la porción coincidente /api/ y la sustituye por /.

4. El Problema de la Pérdida de IP Real del Cliente

Cuando NGINX actúa como intermediario, es él quien establece la conexión TCP final con el servidor de aplicaciones. Como resultado, si tu código Python inspecciona request.client.host, observará:

python • Lo que ve FastAPI sin cabeceras de proxy
# En tu endpoint FastAPI:
@app.get("/whoami")
def whoami(request: Request):
    return {"client_ip": request.client.host}

# Respuesta si no configuraste cabeceras en Nginx:
# {"client_ip": "127.0.0.1"}   <--- ¡TODOS LOS CLIENTES TIENEN LA MISMA IP!

Esto rompe los sistemas de auditoría, prevención de fraude, geolocalización y los límites de peticiones basados en IP. Para solucionarlo, NGINX debe inyectar obligatoriamente las cabeceras estándar de la industria:

nginx • Bloque de Reverse Proxy de Producción
location /api/ {
    proxy_pass http://127.0.0.1:8000;

    # 1. Preservar el dominio original solicitado (ej. midominio.com en vez de localhost)
    proxy_set_header Host $host;

    # 2. Enviar la IP física real del cliente
    proxy_set_header X-Real-IP $remote_addr;

    # 3. Mantener la cadena completa de proxies intermedios
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

    # 4. Indicar al backend si el cliente original usó http o https
    proxy_set_header X-Forwarded-Proto $scheme;

    # 5. Forzar HTTP/1.1 para permitir Keepalive con el backend
    proxy_http_version 1.1;
    proxy_set_header Connection "";
}

5. Buffering y Streaming para Modelos de IA (LLMs)

Por defecto, NGINX almacena en un búfer interno (buffer) toda la respuesta generada por el backend antes de comenzar a enviársela al cliente (proxy_buffering on;). Esto libera rápidamente los hilos de la aplicación para atender nuevas tareas.

🤖

El Conflicto con Server-Sent Events (SSE) y Streaming de LLMs

Si estás sirviendo un modelo de lenguaje (como Llama 3, Mistral, Ollama o vLLM) que envía tokens palabra por palabra mediante Server-Sent Events (SSE) o StreamingResponse en FastAPI, el buffering de NGINX retendrá los paquetes hasta que el búfer se llene o el modelo termine por completo. El usuario verá una pantalla congelada en blanco durante 10 segundos y luego todo el texto de golpe.

Para permitir que los tokens de IA fluyan en tiempo real hacia el frontend según son generados, desactiva el búfer en la ruta correspondiente:

nginx • Configuración para Streaming y Chatbots de IA
location /api/v1/chat/stream {
    proxy_pass http://llm_backend;

    # Desactivar buffering para transmisión instantánea token por token
    proxy_buffering off;
    proxy_cache off;

    # Timeouts prolongados para modelos pesados o generación de texto largo
    proxy_read_timeout 300s;
    proxy_connect_timeout 75s;

    # Cabeceras necesarias para conexiones persistentes de streaming
    proxy_set_header Connection '';
    proxy_http_version 1.1;
    chunked_transfer_encoding on;
}
