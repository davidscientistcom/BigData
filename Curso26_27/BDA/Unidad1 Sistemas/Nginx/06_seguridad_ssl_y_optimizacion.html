Seguridad, SSL/TLS & Rate Limiting

Terminación SSL moderna, redirección canónica 301, mitigación de ataques DoS con el algoritmo Leaky Bucket (limit_req_zone), cabeceras de blindaje y logs estructurados en JSON.

1. Terminación SSL/TLS y Redirección Canónica HTTPS

La Terminación SSL (SSL Termination) es el patrón arquitectónico por el cual NGINX gestiona el cifrado y descifrado de certificados públicos en el puerto 443, liberando por completo a las aplicaciones internas (FastAPI, Flask o bases de datos) de este pesado cálculo criptográfico:

nginx • Configuración HTTPS con Redirección 301
# BLOQUE 1: Servidor HTTP (Puerto 80)
# Redirige todo el tráfico no seguro de forma permanente a HTTPS
server {
    listen 80;
    server_name api.empresa.com;

    # Redirección 301 Moved Permanently preservando la URI original
    return 301 https://$host$request_uri;
}

# BLOQUE 2: Servidor HTTPS Seguro (Puerto 443)
server {
    listen 443 ssl http2;
    server_name api.empresa.com;

    # Certificados SSL/TLS (Let's Encrypt o Autofirmados)
    ssl_certificate /etc/nginx/ssl/server.crt;
    ssl_certificate_key /etc/nginx/ssl/server.key;

    # Protocolos seguros modernos (PROHIBIR SSLv3, TLS 1.0 y TLS 1.1)
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5:!3DES;
    ssl_prefer_server_ciphers on;

    # Caché de sesiones TLS para acelerar reconexiones (10MB ≈ 40.000 sesiones)
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 1d;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-Proto https;
    }
}

1.1 Generación de Certificado Autofirmado para Pruebas

Para laboratorios locales y entornos de desarrollo, puedes generar un par de certificado y clave privada con openssl en una única línea de terminal:

bash • Creación de certificado X.509 de 2048 bits
# Crear directorio seguro
sudo mkdir -p /etc/nginx/ssl

# Generar clave privada y certificado válido por 365 días
sudo openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout /etc/nginx/ssl/server.key \
  -out /etc/nginx/ssl/server.crt \
  -subj "/C=ES/ST=Alicante/L=SanVicente/O=IESSanVicente/CN=localhost"

# Proteger permisos de la clave privada
sudo chmod 600 /etc/nginx/ssl/server.key

2. Rate Limiting: Mitigación de Ataques DoS y Abuso de APIs

En APIs de Inteligencia Artificial (donde una petición a /api/predict consume valiosos ciclos de GPU), un bot o un script malicioso puede saturar la infraestructura enviando cientos de llamadas simultáneas.

NGINX implementa el algoritmo Leaky Bucket (cubo con fugas): las peticiones se acumulan temporalmente y se procesan a un ritmo constante. Si el cubo desborda, el exceso se rechaza inmediatamente:

Algoritmo Leaky Bucket con NGINX limit_req

La tasa media regula el flujo continuo; la ráfaga (burst) tolera picos breves sin penalizar al usuario legítimo

nginx • Configuración de Rate Limiting
# 1. En el contexto http {}: Definir la zona de memoria compartida
# - $binary_remote_addr: almacena cada IP en solo 4 bytes (ahorro del 75% vs string)
# - zone=api_limit:10m: 10 Megabytes permiten rastrear ~160.000 IPs distintas simultáneas
# - rate=5r/s: Tasa máxima promedio (1 petición cada 200 ms)
limit_req_zone $binary_remote_addr zone=api_limit:10m rate=5r/s;

# Personalizar el código de respuesta HTTP cuando se supera el límite:
limit_req_status 429;

server {
    listen 80;

    # 2. Aplicar la restricción en la location de la API
    location /api/ {
        # burst=10: Permite una ráfaga instantánea de hasta 10 peticiones
        # nodelay: Procesa la ráfaga de inmediato sin retrasar artificialmente
        limit_req zone=api_limit burst=10 nodelay;

        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

3. Hardening: Ocultación de Versión y Cabeceras de Seguridad

El endurecimiento del servidor (Security Hardening) reduce la superficie de ataque frente a escáneres automáticos de vulnerabilidades:

nginx • Cabeceras de blindaje en http {} o server {}
# 1. Ocultar la versión exacta de NGINX en cabeceras y páginas de error
server_tokens off;

# 2. Limitar el tamaño máximo de payload entrante (evita saturación de RAM por uploads)
client_max_body_size 25M;

# 3. Prevenir ataques de Clickjacking (la web no puede embeberse en iframes maliciosos)
add_header X-Frame-Options "SAMEORIGIN" always;

# 4. Forzar al navegador a respetar los tipos MIME declarados (Anti MIME-Sniffing)
add_header X-Content-Type-Options "nosniff" always;

# 5. Activar protección XSS en navegadores antiguos
add_header X-XSS-Protection "1; mode=block" always;

# 6. HSTS: Forzar al navegador a usar siempre HTTPS durante 1 año
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

4. Logging Estructurado en JSON para Big Data

El formato tradicional de logs de NGINX (Combined Log Format) es texto plano separado por espacios difícil de parsear en pipelines de Big Data. En arquitecturas modernas, NGINX puede emitir logs directamente en formato JSON estructurado para ser ingeridos por Elasticsearch, Logstash, Fluentd o Grafana Loki:

nginx • Definición de formato JSON en http {}
log_format json_analytics escape=json
  '{'
    '"timestamp":"$time_iso8601",'
    '"client_ip":"$remote_addr",'
    '"request_method":"$request_method",'
    '"request_uri":"$request_uri",'
    '"status":$status,'
    '"bytes_sent":$body_bytes_sent,'
    '"request_time":$request_time,'           # Tiempo total que duró la petición
    '"upstream_time":"$upstream_response_time",' # Tiempo exacto que tardó FastAPI
    '"user_agent":"$http_user_agent"'
  '}';

access_log /var/log/nginx/analytics.json.log json_analytics;
