Casos Reales y Matriz de Decisión

Aprende a elegir la arquitectura exacta para cada problema de negocio, analiza cómo operan gigantes como Netflix, Uber y Spotify, y pon a prueba tus conocimientos con el cuestionario de certificación de la unidad.

1. Matriz de Decisión del Arquitecto de Datos

No existe la "mejor" arquitectura universal: existe la arquitectura adecuada para un conjunto específico de requisitos de latencia, presupuesto y madurez de equipo. Utiliza esta guía para orientar tus decisiones:

Escenario de Negocio Requisito de Latencia Naturaleza de Datos Arquitectura Recomendada Justificación Técnica
Alertas IoT y Detección de Fraude Bancario Sub-segundo (< 100 ms) Streams continuos infinitos Kappa (Kafka + Flink) Evita la duplicidad de Lambda; permite reaccionar evento a evento sin esperar batches.
Modelos ML Complejos + Dashboard en Vivo Híbrida (Segundos + Horas) Cálculos aproximados en streaming + exactos batch Lambda (Spark + Flink + ES) El algoritmo de ML pesado requiere escanear grafos históricos mientras el streaming da alertas rápidas.
Business Intelligence y Analítica Empresarial Minutos / Horas Tabular, Parquet estructurado Data Lakehouse (Delta / Iceberg) Transacciones ACID garantizadas sobre S3 barato, soporte SQL total y Time Travel para auditorías.
Corporación Multinacional con Múltiples Negocios Heterogénea Silos departamentales descoordinados Data Mesh (DaaP + Plataforma) Descentraliza la propiedad hacia los dominios para eliminar el cuello de botella del equipo central.

2. Casos Reales en la Gran Industria

🍿

Netflix: El Nacimiento de Apache Iceberg

Netflix gestiona más de 100 petabytes en Amazon S3. Al intentar realizar listados de particiones en directorios con millones de archivos, el S3 API colapsaba por latencia. Para solucionarlo, crearon Apache Iceberg, que rastrea los ficheros mediante árboles de metadatos jerárquicos independientes de la estructura de carpetas.

🚗

Uber: La Reinvención con Kappa+

Con millones de viajes y conductores simultáneos, Uber sufría retrasos e inconsistencias contables con su arquitectura Lambda. Su migración hacia Kappa+ con Apache Kafka como log persistente y Apache Flink como motor unificado les permitió procesar más de 40 millones de eventos por segundo en tiempo real.

🎵

Spotify: Recomendaciones y Discover Weekly

Spotify combina una arquitectura event-driven con Kafka para capturar cada reproducción de canción, alimentando modelos de recomendación que ajustan la lista de reproducción en tiempo real, mientras que pipelines batch de Lakehouse computan resúmenes anuales como el célebre Spotify Wrapped.

3. Taller Práctico: Resuelve estos Escenarios de Examen

📋 Caso A: La Startup Fintech

Situación: Una startup de 25 empleados lanza una app de pagos móviles. Tienen 2 ingenieros de datos y el CEO sugiere implementar Data Mesh porque lo leyó en un blog.

Tu dictamen como Arquitecto: Rotundamente NO. Data Mesh exige decenas de desarrolladores y múltiples dominios. Para 2 ingenieros, introducir Data Mesh creará una sobrecarga burocrática letal. Deben usar un Lakehouse centralizado (ej. DuckDB o Databricks sobre S3) que les dará valor inmediato con coste mínimo.

📋 Caso B: Cadena de Supermercados con Fraude en Cajas

Situación: Quieren bloquear cobros irregulares en menos de 500 ms y a la vez generar el informe fiscal consolidado de cierre contable a las 23:59 con exactitud de céntimos.

Tu dictamen como Arquitecto: Arquitectura Kappa con Serving Layer Dual o Lakehouse Streaming. Un topic de Kafka captura los tickets; un motor de streaming (Flink) evalúa reglas de fraude en 50 ms, y vuelca los eventos a tablas Iceberg/Delta Lake para el cuadre contable.

4. Cuestionario de Autoevaluación de la Unidad

Selecciona la opción correcta en cada pregunta para comprobar tu asimilación técnica de los conceptos:

1. Según el Teorema CAP de Eric Brewer, ¿por qué ningún sistema Big Data distribuido puede ser clasificado como puramente "CA"?
A) Porque el hardware moderno no soporta discos de alta velocidad.
B) Porque en una red real los cortes y latencias son inevitables, haciendo que la Tolerancia a Particiones (P) sea obligatoria.
C) Porque el modelo relacional de Codd prohíbe el particionamiento de datos.
2. ¿Cuál es el principal inconveniente que llevó a la industria a buscar alternativas a la Arquitectura Lambda?
A) Que no permite procesar datos en tiempo real.
B) El "Infierno del Doble Código": mantener dos bases de código separadas para batch y streaming con la misma lógica.
C) Que el Master Dataset en HDFS pierde datos constantemente.
3. En la Arquitectura Kappa propuesta por Jay Kreps, ¿cómo se recalcula la historia si se introduce una corrección en el código?
A) Lanzando un trabajo nocturno de MapReduce sobre Hadoop.
B) Desplegando una nueva versión del trabajo de streaming desde el offset 0 del log de Kafka (Replay) hacia una nueva vista.
C) Editando manualmente los mensajes erróneos dentro de los topics de Kafka.
4. ¿Qué ventaja fundamental aporta un Data Lakehouse (Delta Lake / Apache Iceberg) frente a un Data Lake clásico en S3?
A) Que sustituye el formato Parquet por bases de datos relacionales SQLite.
B) Transacciones ACID, prevención de datos corruptos, Time Travel (viaje en el tiempo) y cumplimiento de esquemas.
C) Que prohíbe el uso de sentencias SQL para forzar el uso de C++.
5. En el paradigma Data Mesh de Zhamak Dehghani, ¿qué significa el principio de "El Dato como Producto" (Data as a Product)?
A) Que la empresa debe vender sus datos en un marketplace de internet para obtener beneficios.
B) Que los datos se tratan con la misma seriedad que un producto de software: con SLAs, documentación, propietario y calidad garantizada.
C) Que el equipo central de ingenieros de datos es el único responsable de la calidad de todas las tablas.
